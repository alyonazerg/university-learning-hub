# Campus messages

Teacher Hub and the student Learning Hub share the `Messages` section. Each registered student has a private conversation with the platform teacher. Teachers can also send to one group, several selected groups, or all active groups. These are broadcast messages delivered into each student's private conversation; student replies remain private. This version does not offer shared group chats, student-to-student messages, email delivery or closed-app push notifications.

Broadcasts are saved with a snapshot of recipients in `message_broadcasts` (`025_message_broadcasts`). Inactive students and groups are excluded. Repeating the same request returns the existing delivery result and does not send again or add newly joined students. The teacher can view sent broadcasts and recipient counts. Individual messages carry a group label when sent as part of a broadcast.

Messages are stored in PostgreSQL (`024_campus_messages`). The API under `/learning/messages` always checks the active session and conversation ownership. Student requests cannot read or write another student's conversation. Teachers can find students by alias and group. `request_id` makes retries idempotent. Message content is plain text and displayed through `textContent`.

The client opens an authenticated SSE connection at `/learning/messages/events`. The backend checks message/read changes each second and sends a small event; the client then fetches the updated thread. Connections reconnect after interruption and stop on logout or session expiry. Read receipts are set only for incoming messages rendered in the active section. Drafts stay in the browser session; failed requests keep the composed text. Earlier messages can be loaded in batches. Unicode emoji are inserted through the shared `emoji-picker.js` component, also used for IMT feedback.

Messages includes an opt-in browser notification control and a sound toggle. A short Web Audio chime plays when browser autoplay policy allows it after a user gesture. Notification text does not include private message content. The service worker only handles notification display/clicks; it does not receive push events or cache API responses. Closed-app notifications need a separate Web Push subscription/delivery service, especially for installed iOS PWAs. Browser suspension can pause live delivery on mobile.

Telegram copies use the existing `TELEGRAM_BOT_TOKEN` through `telegram_messages.py`. Each student opts in through Messages → Telegram alerts and must start the bot. Teachers connect a verified Telegram account using the widget; this single-teacher platform stores one destination. New private and broadcast messages are delivered in a background task with a campus link. Delivery state is stored on the message; external failures leave campus messages untouched. This does not implement replies from Telegram, scheduled retries or a durable external worker. Teacher Telegram linking requires the same BotFather domain configuration as student login.

The shared `campus-home.js` routes the logo to the authenticated Home section, falling back to public landing for expired/absent sessions. Role-specific cards use existing coursework, group, IMT and timetable data. No fabricated progress figures are shown.

Relevant checks: `backend/tests/test_messages.py`. Teacher sessions are shared by the current admin role; separate staff identities or permissions require an account model change.
